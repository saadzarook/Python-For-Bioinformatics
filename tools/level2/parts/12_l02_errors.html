Lesson 2When things go wrong

🧬 Why this matters in bioinformatics

Real data breaks programs. A file is cut short, a sequence contains an X, a spreadsheet says n/a instead of a number. A good pipeline doesn't hide these problems or, worse, quietly produce wrong numbers. It stops with a clear message, or deals with the problem on purpose. In this lesson you'll learn to read errors, catch them, raise your own, and test your code so bugs show up early.

First, a reminder from Level 1 that's worth repeating: errors are not failures. They are clues. Everyone gets them, all the time. The skill isn't avoiding errors; it's reading them calmly and working out what they're telling you.

Reading a full traceback

In Level 1 your errors were mostly one line deep. Once functions call other functions, the error report, called a traceback, lists every step that led to the problem. Here's what you'd see on your own computer if you ran this small script, called analysis.py:

💻 analysis.pyon your own computer
def gc_content(seq):
    """Return the GC content of a DNA sequence, as a percentage."""
    return (seq.count("G") + seq.count("C")) / len(seq) * 100


def report(sequences):
    """Print the GC content of every sequence in a dictionary."""
    for name, seq in sequences.items():
        print(f"{name}: {gc_content(seq):.1f}% GC")


samples = {"S01": "ATGGTGCAT", "S02": "", "S03": "GGCC"}
report(samples)

What Python prints

S01: 44.4% GC
Traceback (most recent call last):
  File "/home/you/project/analysis.py", line 13, in <module>
    report(samples)
    ~~~~~~^^^^^^^^^
  File "/home/you/project/analysis.py", line 9, in report
    print(f"{name}: {gc_content(seq):.1f}% GC")
                     ~~~~~~~~~~^^^^^
  File "/home/you/project/analysis.py", line 3, in gc_content
    return (seq.count("G") + seq.count("C")) / len(seq) * 100
           ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~^~~~~~~~~~
ZeroDivisionError: division by zero

How to read it:

  1. Start at the bottom. The last line says what went wrong: ZeroDivisionError: division by zero.
  2. Read upwards to see where. "Most recent call last" means the deepest step is at the bottom: line 3, inside gc_content. Just above it, line 9 in report is the line that called gc_content, and line 13 called report.
  3. Ask why. Dividing by len(seq) failed, so len(seq) was 0. Sample S02 is an empty sequence!

The little ~~~^^^ marks point at the exact part of the line that failed. Notice that S01 was printed before the crash: Python ran everything up to the problem. This page shows a shorter, friendlier version of the same information. Try it:

Catching errors with try / except

Sometimes you expect a problem and know what to do about it. Say your read counts come from a spreadsheet, and someone typed n/a for a failed sample. int("n/a") raises a ValueError. With try / except you can catch that one kind of error and carry on:

  • Python runs the indented lines under try:.
  • If one of them raises a ValueError, Python jumps straight to the except ValueError: block instead of stopping.
  • If nothing goes wrong, the except block is skipped.

🧹 Good habit: catch only what you expect

Always name the error you expect, like except ValueError:. A bare except: (with no error name) catches everything, including your own typos, so real bugs silently disappear and you get wrong results with no warning. If you don't know what to do about an error, it's better to let the program stop.

Raising your own errors

Python can't know that "ATGXC" isn't valid DNA: to Python it's just text. You know, so you can tell it. raise stops the program with an error of your choice and a message you write. ValueError is the usual choice for "this value isn't acceptable":

That error is a good thing! Instead of quietly calculating a GC content that includes an X, the program stops and tells you exactly what's wrong and where. This is called "failing loudly", and it's one of the best habits you can build.

Debugging with print()

The sneakiest bugs don't raise any error: the code runs and gives a wrong answer. A debugging trick that every programmer uses, beginners and experts alike, is to print the values in the middle of the code to see where reality differs from what you expected. Python has a handy shortcut for this: f"{gc=}" prints both the name and the value.

The debug line shows gc=0 for the lowercase sequence: .count("G") doesn't count g. The fix is seq = seq.upper() at the start of the function. Once the bug is fixed, delete the debug line.

Checking your code with assert

assert checks that something is true. If it is, nothing happens. If it isn't, Python stops with an AssertionError and your message. It's the simplest way to test a function: try it on tiny examples where you already know the right answer.

Now change pairs so that "G": "G" (a typo you could easily make), and run again. The tests catch it immediately.

🧹 Good habit: test with small, known examples first

Before running a function on 10 million reads, run it on three bases where you can work out the answer in your head. If it's right on tiny examples, you can trust it much more on big data. The Check my answer button on this page works exactly like this: it's a set of assert lines!

⚠️ Careful with decimals

Computers store decimals with tiny rounding errors: 0.1 + 0.2 == 0.3 is False! When testing decimal results, round them first: assert round(gc_content("GATTACA"), 2) == 28.57.

Quick quiz

1. A traceback is several lines long. Where do you look first?

  • The first line just says "Traceback (most recent call last)". The useful part is at the bottom.
  • Right: the last line names the error, and the lines above it show the chain of calls that led there.
  • Start at the bottom: it says what went wrong. Then read upwards for where.

2. Which except catches the error from int("n/a")?

  • KeyError is for missing dictionary keys. Converting bad text to a number is a ValueError.
  • Correct: the text has the right type (a string) but an unsuitable value.
  • Nothing is divided here.

3. What does raise ValueError("Invalid base 'X'") do?

  • Yes. The code that called the function can catch it with try/except, or let it stop the program.
  • That's what print() does. raise really stops, unless the error is caught.
  • raise never changes data. It reports a problem.

4. assert gc_content("GGCC") == 100 runs and nothing appears. What does that mean?

  • Right: assert is silent when the condition is True. It only speaks up when something is wrong.
  • It wasn't skipped. A passing assert simply has nothing to say.
  • Then gc_content would give None, None == 100 would be False, and the assert would fail loudly.
✅ Key takeaways
  • Read a traceback from the bottom up: the last line says what went wrong, the lines above show where.
  • try / except SomeError: handles an error you expect. Always name the error you expect.
  • raise ValueError("clear message") fails loudly on bad input, instead of producing wrong results.
  • Debug by printing values in the middle of the code: print(f"{x=}").
  • Test functions with assert on small examples where you know the answer.
