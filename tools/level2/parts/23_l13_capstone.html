Lesson 13Capstone: a mini analysis pipeline

🧬 Why this matters in bioinformatics

Every sequencing project starts the same way: raw reads come off the machine, and someone has to check them, filter them, summarise them and report what they found, before any biology can happen. That "someone" usually writes a pipeline: a script that runs every step, in order, the same way every time. In this capstone, you'll build one from start to finish using almost everything from Level 2.

The plan

run42.fastq (raw reads, never changed)
   │
   ├─ 1. measure every read      (Biopython, functions)       → length, mean quality, GC%, N count
   ├─ 2. quality control         (named thresholds)            → passed / failed
   ├─ 3. build a table           (pandas)                      → run42_read_stats.csv
   ├─ 4. keep the good reads     (SeqIO.write)                 → run42_passed.fastq
   ├─ 5. plot                    (matplotlib)                  → quality and GC distributions
   └─ 6. summarise               (f-strings, files)            → run42_summary.txt

The data is run42.fastq from Lesson 9: 40 reads of 75 bases, made-up teaching data built from real human gene sequences with simulated, realistic quality scores.

One new tool: SeqIO.write(records, filename, "fastq") writes a list of SeqRecords to a file. It's the partner of SeqIO.parse(), and it works for FASTA too.

🧹 Good habits you'll see in this pipeline
  • All settings and file names are named constants at the top, so anyone can see and change them in one place.
  • Small functions with docstrings, each doing one job.
  • The functions are tested on tiny examples with assert before they touch the real data.
  • The raw file is only read; every result goes to a new file.
  • The software versions are printed with the results, for reproducibility.

🧪 Capstone

Capstone✍️ Write itQuality control for run42

Complete the two functions, then run the whole pipeline:

  • read_stats(record) receives one Biopython FASTQ record and returns a dictionary with the keys "read_id", "length", "mean_quality", "gc_percent" and "n_count" (the number of N bases).
  • passes_qc(stats, min_mean_quality, max_n_bases) returns True if the read's mean quality is at least min_mean_quality and it has no more than max_n_bases N bases.

The tiny tests in the middle of the program check your functions before the real data is touched; if one fails, its message tells you what to fix. Everything after the tests is already written. Check my answer runs the whole pipeline and checks every output file. When it all works, replace the MY_CONCLUSION text with a sentence or two of your own about what the results mean.

read_stats: the five values are record.id, len(seq), mean(scores), (seq.count("G") + seq.count("C")) / len(seq) * 100 and seq.count("N"). Put them in a dictionary with the right keys.

passes_qc: one line does it: return stats["mean_quality"] >= min_mean_quality and stats["n_count"] <= max_n_bases. Use the parameters, not the constants, inside the function.

If a test fails, its message names the function and the key. Fix one thing at a time and run again: that's exactly how pipelines get built.

What we found

When your pipeline runs, you should see this (your conclusion will be your own):

  • 32 of 40 reads (80%) passed QC. The failed reads averaged about Q19 against Q33 for the passed reads, and the two reads with an unknown base (N) were among the failed ones.
  • The read-quality histogram has two clear humps, and the threshold of Q25 sits in the gap between them. Choosing a threshold by looking at the data, and then writing down why, is exactly what analysts do.
  • The GC content of the passed reads clusters around 50–60% (median 52.7%), as expected for human coding sequences such as HBB and INS. No second hump, so no sign of contamination.
  • Even the passed reads lose quality towards their 3′ end, from about Q35 down to about Q26. A next step could be trimming their 3′ ends, using the trim_end() function from Lesson 5.

A short written summary like this, saved next to the numbers and plots, is what turns a script's output into a result a colleague can use. You've just done the full job: read → check → filter → summarise → plot → report. That's what real bioinformatics pipelines do, on hundreds of millions of reads at a time. 🎉

🤓 Did you know?

Real projects use exactly these steps, with industrial-strength tools: FastQC and MultiQC for the quality reports, fastp or Trimmomatic for filtering and trimming, and workflow managers such as Snakemake or Nextflow to run every step for hundreds of samples. Under the hood, they're doing what your pipeline does.

Quick quiz

1. Why does the pipeline test read_stats() on a 6-base read before running on the real file?

  • Exactly. It's much easier to check 6 bases by hand than 40 reads of 75 bases.
  • Biopython doesn't need a warm-up. The tests are for our own code.
  • Tests add a tiny bit of time; their value is catching mistakes.

2. Your supervisor asks you to rerun the analysis with a threshold of Q28. What do you change?

  • Yes: that's the payoff of named constants. Everything else, including the summary, updates automatically.
  • With a named constant, there's only one place to change.
  • Never edit raw data. Change the setting and rerun the code.

3. Why does the summary file include the software versions and settings?

  • It's not decoration: it's what makes the result repeatable.
  • Right. Different versions or thresholds can give different numbers.
  • Nothing requires it. It's a reproducibility habit.
✅ Key takeaways
  • A pipeline runs every step in order, the same way every time: read → check → filter → summarise → plot → report.
  • Settings at the top, small tested functions, raw data untouched, results in new files, versions recorded.
  • SeqIO.write(records, filename, "fastq") saves SeqRecords to a file.
  • Results aren't finished until they're summarised in words someone else can understand.
